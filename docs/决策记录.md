## D-002 · T2 用户与权限

**日期**：2026-11-22　**状态**：核心已定，子项未定

### 结论

| 项 | 结论 |
|---|---|
| 用户来源 | **双轨**：① 邀请制（管理员后台手工开号）② 开放注册（需邮箱验证） |
| 服务访问隔离 | **网关拦截**：nginx 在转发到内网服务前，先向鉴权服务确认"此人对此服务有无权限"，无权限返回登录/无权限页 |
| 评论 | **自建评论系统**（不用 giscus，不依赖 GitHub 账号） |
| 访问统计 | **只做阅读量计数**，不做访客画像、不做第三方脚本 |

### 依据

- 服务里有些要对外开放、有些只给特定人看，两种状态不够用，必须支持逐服务授权。
- "隐藏卡片"只是视觉手段，服务本身仍在内网可达；只有网关拦截才是真隔离。

### 未定子项（下次接着谈）

| # | 子项 | 说明 |
|---|---|---|
| 1 | 角色怎么分 | 候选：`admin` / `member`（受邀）/ `user`（自助注册）/ `guest`（未登录）。是否还需要"临时访客链接" |
| 2 | 授权粒度 | 到服务级就够，还是需要"服务内的某个页面"级 |
| 3 | 邮箱验证怎么做 | 自建 SMTP 发信（需要邮箱服务商）／ 接第三方发信 API；拒收/退信怎么处理 |
| 4 | 找回密码 | 邮件链接重置；重置链接有效期与一次性 |
| 5 | 会话策略 | 单设备 or 多设备；记住我多久；能否踢下线 |
| 6 | 注册防滥用 | 图形验证码、频率限制、是否需要邀请码才能注册 |
| 7 | 用户资料 | 需要哪些字段（昵称、头像、简介）；能否自行注销 |
| 8 | 隐私 | 收集了邮箱与访问数据，需要一份隐私说明页面 |

### 代价与影响（诚实记录）

- 这是本项目最大的一次范围扩张：从"单人站"变成"小型社区平台"。
- 新增子系统：注册、邮箱验证、找回密码、角色管理、逐服务授权、邀请码、审计。
- 新增数据表（初估）：`users`、`roles`、`user_roles`、`service_acl`、`invites`、`email_tokens`、`sessions`。
- 新增组件：鉴权服务的一个端点 `/api/auth/verify`（供 nginx 调用）+ nginx `auth_request` 配置。
- 评论系统自带一整套问题：防垃圾、审核、XSS 过滤、通知。
- 安全要求相应提高：所有用户输入都要校验；上传要防滥用；注册口要有频率限制与验证码。

## D-004 · T5 主题与视觉（第二轮）

**日期**：2026-11-22　**状态**：等待用户提供主题构思文档　**取代**：D-003 中"以 try/ 素材为依据"的部分

### 结论

| 项 | 结论 |
|---|---|
| `try/` 素材 | **全部作废**，与项目无关（只是实验 CSS 属性的地方）。不作为主题依据，也不再作为技术参考 |
| 沉浸层级最终目标 | **L3：全 3D 导航**（在三维场景中移动视角并进入服务） |
| 门户形态 | 倾向"主题化列表 + 静态页面"的结合，**可行性待验证**，见下 |
| 配色套数 | 一套为主；是否要浅色由主题决定 |
| 现有雏形（深紫+粉紫+玻璃） | 全部推翻，等用户重新描述 |

### L3 带来的硬约束（现在就必须遵守，否则后期大返工）

| # | 约束 | 原因 | 后果 |
|---|---|---|---|
| 1 | **服务数据必须能表达"空间位置"** | 3D 场景里每个服务是一个实体，需要坐标/区域/朝向/尺寸等字段 | 数据表在 P2 就要预留这些字段，不能只存 `name + url` |
| 2 | **场景状态必须与 URL 同步** | 相机在哪、进了哪个区域，要能分享链接、能前进后退 | 路由设计要按"区域/实体"分层，如 `/explore/:zone` |
| 3 | **必须存在非 3D 的等价路径** | 手机低端机、无障碍读屏、搜索引擎、关掉 WebGL 的浏览器 | 每个 3D 入口都要有一份等价的普通页面/列表，数据同源 |
| 4 | **首屏必须能"先出 2D 骨架再渐进增强"** | 3D 引擎体积大，等它加载完再显示白屏是不可接受的 | 骨架屏 → 背景 → 场景，分三段加载，任一段失败都不影响可用性 |
| 5 | **博客正文与后台不进 3D** | 长文阅读与三维界面互斥 | 3D 只负责入口层；进入内容自动降级为 2D 静态页面 |

### 对"主题化列表 + 静态页面结合"的初判

**可行**，而且这基本是所有成功案例的标准结构：

```
3D 场景（入口层）        ←→  普通页面（内容层）
  · 视角移动、节点可点            · 文章、评论、账号、后台
  · 节点 = 服务/区域               · 与场景共享同一份数据
  · 手机/降级时自动切到列表视图
```

场景不是替代页面，是**页面之上的一层入口**。用户点场景里的节点 → 进入普通页面 → 页面顶部有个"返回场景"。

## D-008 · 文档架构：让项目状态不依赖会话上下文

**日期**：2026-11-23　**状态**：已定　**依据**：作者提出"新建用户画像目录 + 学习情况也要记进项目文档，确保其他会话和智能体能接手"

|---|---|---|
| **入口层** | `AGENTS.md` 的 0.5 节 + `docs/README.md` | 告诉任何来者"去哪找什么"，含交接检查单与优先级链 |

| **依据层** | `设计.md`、`主题.md`、`决策记录.md`、`实施细节.md`、`开发历程.md` | 写"是什么/为什么"，按各自规则改 |

### 关键设计

1. **用户画像独立成目录** `docs/用户画像/`：基本情况 / 技术水平 / 偏好与协作 / 目标与动机。
2. **优先级链写死在 `docs/README.md`**：运行时行为 > 决策记录最新条 > 设计.md > 领域文档 > 实施细节 > README。
3. **状态与决策分离**：状态文件写"现在"，决策文件写"为什么"，并规定"状态文件不许写历史"。
4. **AGENTS.md 瘦身**：删掉与 docs 重复的旧内容（M0–M5 计划、六区目录、try/ 作为主题依据），只留稳定规矩 + 文档地图。
5. **明确作废项**：`try/` 不是项目依据；`内容.txt` 不是内容依据。
6. **`docs/开发历程.md` 补齐**（AGENTS.md 早就要求但一直没建）。

### 顺带产生的校准

作者修正的三条水平假设（TS 不懂类型注解 / JS 不会接到 HTML / CSS 会写但不稳）已写入 `用户画像/技术水平.md`，并据此给阶段 A 增加 **A-4 CSS 排错微模块**、把阶段 A 从 3 周调为 3.5 周（允许延至 5 周）。

## D-009 · 文档自动更新授权 + 汇报节奏

**日期**：2026-11-23　**状态**：已定　**依据**：作者要求"文档在需要更新的时候由你自动更新，免得讲了半天我以为记进去了其实没有动"；以及"文档里有说明我什么时候应该向你提交报告吗？"

### 问题一：汇报节奏此前没写死

查过：`学习计划/00-总览.md` 只有"每完成一个阶段汇报"一句，没有说清"练习级""卡住时""会话结束时"该怎么办。已补。

### 问题二：更新责任此前模糊

此前 AGENTS.md 写的是"默认只读，除非当轮明确要求"，导致文档可能该更新而没更新。已改为**文档默认自动更新**，代码/依赖/git 仍默认只读。

### 结论一：汇报节奏（写在 `学习计划/README.md`）

| 触发器 | 汇报形式 |
|---|---|
| 完成一个练习 | 轻量 3 行（做了什么 / 卡在哪 / 用时） |
| 完成一个子阶段（A-1…A-4） | 完整模板（`00-总览.md` 第 6 节） |
| 卡住超过 40 分钟 | 立即求助（报错原文 + 完整代码 + 疑似行） |
| 每次会话结束 | 一句话；助手据此更新 `进度.md` 与 `项目状态.md` |
| 连续 2 周无进展 | 停下来聊 |

硬规矩：`进度.md` 里没勾 = 没做过。汇报判据是"有代码可看"，不是"看完了视频"。

### 结论二：更新权限矩阵（写在 `docs/README.md` 5.1）

| 类别 | 文件 | 规则 |
|---|---|---|
| ✅ 自动 | `项目状态.md`、`学习计划/进度.md`、`用户画像/*`、`开发历程.md`、`决策记录.md`、`实施细节.md`、`README.md` | 发现需要就直接改，无需请示 |
| ⚠️ 有条件 | `设计.md` 正文（议题谈定后 + 写变更记录）、`主题.md` 的 M 节之后、`学习计划/00–04`（改了要留 D-xxx）、`AGENTS.md`（稳定规矩变化时） | 可改，但必须留痕/说明 |
| ❌ 禁止 | `主题.md` 的 **A–L 节**（作者原文） | 只能追加，不能改写 |
| 🔒 仍需明确要求 | 代码、依赖安装、`git commit/push`、删除文件 | 一句"帮我改"才动手 |

### 结论三：可检查的承诺（防止"以为记进去了"）

助手每次改文档必须在回复里报一行：

```
📄 已更新：<文件> → <改了什么> → <为什么>
```

**没看到这一行 = 真的没改。** 这是作者用来核对的手段，也是助手的自我约束。若某次该改却因硬约束没改，必须显式说"这份我没动，因为 X，需要你确认"。

### 自动更新不包括什么

需要**作者本人判断**的内容，助手不会替他填：配色二选一、角色形态、内容清单（T7）、域名记录操作、以及任何"我不确定他想要什么"的决定。这些一律列进 `项目状态.md` 的阻塞项。
