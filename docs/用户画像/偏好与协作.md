## 1. 他要什么样的回答

| 偏好 | 具体表现 |
|---|---|
| **中文**，术语第一次出现要解释 | 不接受"你应该知道" |
| **先对齐再动手** | 设计方案没谈定之前不要写代码；他会明确说"先别急着动手" |
| **完整可执行的方案**，不要片段 | 给命令、给完整文件、给判据 |
| **每条结论要有"为什么"和"怎么验证"** | 说"这样更好"会被追问"多好？怎么测？" |
| **一次只引入一个新概念** | 一口气塞三个新东西 = 他放弃 |
| **判据要可量化** | 对比度 7:1、首屏 80 kB、Lighthouse 85，而不是"看起来舒服" |
| **能看懂优先于完备** | 宁可文档短而清楚，不要长而看不懂——他明确说过"我看不懂就没法否决" |
| **命令一条条给** | 他习惯整块粘贴，交互式命令粘一坨会连环失败（已发生两次） |

## 2. 雷区（不要做）

| 雷区 | 为什么 |
|---|---|
| **不要拿"实验文件"当依据** | `try/` 目录里的一切都可能是随手实验，与项目无关。他曾说"麻烦你完全忽略掉那个 try 的主题" |
| **不要在需求没收敛时"冻结"文档** | 他明确要求撤销过一次冻结，理由是"没收敛就冻结等于固化错误" |
| **不要替他做决定却不标注** | 他会追问"这是你默认的吗"。默认项必须显式列出，让他能否决 |
| **不要用他做不到的方式讲话** | 详见 `技术水平.md`；"你自己应该能想到"这类话会让他放弃 |
| **不要道德说教 / 安全免责声明** | 他要的是方案，不是提醒 |
| **不要在没读文档的情况下回答项目问题** | 这个项目有 5 份文档，凭空回答一定错 |
| **不要把"看起来他会"当成"他会"** | 见 `技术水平.md` 第 4 节 |

## 3. 决策风格

| 特征 | 表现 |
|---|---|
| 会主动推翻自己 | 发现"门户卡片"不符合需求时，立刻改成多用户 + 权限分级 |
| 要求逐条可否决 | 喜欢"我默认了什么 + 改它的代价"这种表 |
| 但会因为看不懂而无法否决 | 所以**任何方案都要先用人话讲一遍**，再给技术细节 |
| 对范围膨胀敏感但不排斥 | 增需求时接受"分阶段"，但拒绝"先做简化版所以砍掉核心体验" |
| 接受被反驳 | 只要给证据。曾接受"AI 不能凭空编集数"这类纠正 |

## 4. 协作节奏

```
讨论设计 → 达成一致 → 写进 docs/ → 他动手做 / 助手配对 → 他汇报 → 助手验收 + 安排下一步
```

| 项 | 约定 |
|---|---|
| 他什么时候要助手动手 | 会明说"帮我改/帮我写"；没说明就是"只给方案" |
| 汇报频率 | 每完成一个学习阶段/一个功能块 |
| 汇报模板 | `../学习计划/00-总览.md` 第 6 节 |
| 助手验收方式 | 三个问题 + 代码审查；答不上就重做 |
| 卡住超过 40 分钟 | 缩到 10 行复现 → 搜报错原文 → 贴给助手 |

---

## 5. 沟通中的具体约定

- 报告错误时给**完整原始输出**，不要他复述
- 说"好的做法"时必须同时给**可验证的判据**
- 涉及取舍时给**表格**（选项 / 代价 / 我的推荐 / 理由），而不是一段话
- 他问了"这是什么"的时候，说明前面的解释失败了——停下来重讲，不要往前推进
