## 0. 怎么读这份文档

只回答"建什么、不建什么、什么算做完"，不回答"代码怎么写"。每节都能被你自己验证。

**术语表**

| 词 | 一句话 |
|---|---|
| 前端 | 浏览器里跑的代码，管长什么样、点了去哪 |
| 后端 | 一直开着的一个程序，管存进去、读出来、验身份 |
| 数据库 | 一个文件 `app.db`，用 SQL 语言读写 |
| 接口 / API | 前后端约定的"问一句答一句"的地址，形如 `/api/posts` |
| **静帧** | 一张事先渲染好的高清图片，当背景用（本项目首页书房就是静帧） |
| **锚点（anchor）** | 场景里某个物件的三维坐标，用来把 HTML 卡片对齐到桌面上 |
| **网关** | 所有请求先进的一道门；本项目里是云上的 nginx |
| **网关拦截** | 门在转发前先问鉴权服务"这人对这服务有权限吗"，没权限就挡回去 |
| **角色** | 一组权限的名字，如 `admin` / `member` / `user` |
| **ACL** | 某个具体服务允许哪些角色访问的那条记录 |
| 隧道 | 两台内网机器之间的加密私线（本项目用现成 Tailscale） |
| 哈希 | 单向加密，能验不能还原，密码这样存 |
| TOTP | 手机验证器上每 30 秒变一次的 6 位码 |
| systemd | Linux 自带的服务管家，开机自启、挂了重启 |
| 部署 | 把新版本放上去并让它运行 |

## 1. 项目目标

**一个域名下同时是**：一间可以走进去的书房（入口）、一座可读可写的图书馆（博客与随笔）、一柜可以取用的器物（自建服务门户与服务器管理），并且**可以开号给别人用**。

同时它是**为 agent 全栈开发实习准备的练手项目**——每一块自己写、自己排错。

**不做清单（截至 v0.3）**

| 不做 | 理由 |
|---|---|
| 富文本编辑器 | 用 Markdown + 快捷键 + 悬浮工具条替代；富文本是拖期头号原因（D-001） |
| 网页里的任意命令输入框 | 控制台只做"预设按钮"；需要终端时用现成 web 终端挂内网 + Tailscale（D-001） |
| 微服务 / 消息队列 / 缓存中间件 | 单体 + 单数据库足够（D-001） |
| Prometheus + Grafana | 先用 psutil 直接读，需要趋势与告警时再评估（D-001） |
| 多人实时协作编辑 | 单作者，不需要 OT/CRDT |
| 移动端 App | 响应式网页足够 |

### 2.3 三级导航（主题决定的结构）

```
L1  首页书房        静帧背景 + DOM 投影卡片（视觉重头戏）
       │ 点物件 / 滚动 / "结构图"按钮
       ▼
L2  图书馆结构图    一张俯视图 + 可点热区（成本极低）
       │ 点热区
       ▼
L3  功能区场景      每个功能区都有自己的场景与交互（不是普通网页）
                    博客（藏书库）/ 随笔（奇物收藏室）/ 文件传输（借阅室）
                    / 实验室 / 核心区 / 用户个人空间 / 以后还会加
```

**三级都是场景，不是只有 L1。** 区别在投入：L1 是精心设计的书房，L3 每个区域是"同一套场景机制 + 各自的静帧与物件"。这带来一个硬要求（见 2.4）。

### 2.4 场景注册表（可扩展的核心）

每个场景是一份自包含的数据，**加一个场景不等于改一处代码**：

```
scenes/<sceneId>/
  ├─ manifest.json     # 相机参数、锚点、热区、渲染器类型、降级图
  ├─ still.webp        # 静帧（V1 渲染器）
  ├─ still@2x.webp     # 高分屏
  └─ still-mobile.webp # 手机裁切版
```

```jsonc
// manifest.json
{
  "id": "study",                    // 书房
  "title": "书房",
  "renderer": "still",              // "still" | "webgl"  ← 静帧换 3D 只改这一个值
  "camera": { "pos": [3.62,2.46,5.72], "yaw": 0, "pitch": -30, "hfov": 63, "aspect": 1.7768 },
  "anchors": {
    "desk":      { "world": [0.2,0.78,0.4],  "normal": [0,1,0], "size": [1.6,0.9] },
    "bookshelf": { "world": [-1.8,1.6,-2.3], "normal": [0,0,1], "size": [1.2,1.8] }
  },
  "hotspots": [
    { "id": "to-library", "anchor": "bookshelf", "label": "藏书库", "goto": "/explore/library" }
  ],
  "fallback": { "still": "still.webp", "text": "藏书库（列表视图）" }
}
```

四条规则：

1. **新增场景 = 新增一个目录**，路由 `/explore/:sceneId` 自动识别，不改路由表。
2. `renderer` 字段是"静帧→3D"的开关：V1 全部 `still`；学到 Three.js 后逐个场景改成 `webgl`，**数据、锚点、热区、DOM 层全部复用**。
3. 每个场景必须带 `fallback.text`——3D/图片都加载不出来时，用户看到的是一份可读的列表，不是空白。
4. 场景之间用 `hotspots[].goto` 连线；L2 结构图本身也是一个场景（俯视图 + 热区）。

**为什么要注册表而不是写死**：功能区会持续增加（用户个人空间、以后新服务），写死的话每加一个就要动路由、导航、类型定义三处；注册表方式只加目录。

## 4. 权限模型

### 4.1 三层身份

| 角色 | 怎么来 | 默认能做什么 |
|---|---|---|
| `guest` | 未登录 | 看公开内容、看标记为公开的服务卡片 |
| `user` | 自助注册 + 邮箱验证 | 看标记为 user 的内容与服务、发评论 |
| `member` | 管理员邀请开号 | 全部 user 权限 + 受邀可见的服务 |
| `admin` | 只有你 | 写作、管理用户、控制台 |

（是否需要第五种"临时访客链接"，待 T3 定。）

### 4.2 逐服务授权

每个服务一条记录，带可见性与准入规则：

| 字段 | 例 |
|---|---|
| `slug` | `astar` |
| `title` / `desc` / `icon` | A* 可视化 / … / … |
| `visibility` | `public` \| `user` \| `member` \| `admin` |
| `allow_users` | 额外放行的具体用户（可选） |
| `upstream` | 内网地址，如 `http://100.64.0.35:8081` |
| `scene_slot` | 在 L1 场景里的锚点名（`bookshelf` 等） |

### 4.3 关键是"网关拦截"而不是"藏卡片"

```
请求 /svc/astar
  → 云上 nginx
  → auth_request 子请求：GET /api/auth/verify?service=astar（带上用户 cookie）
       ├─ 200 + X-User-Id → 放行，反代到 upstream
       └─ 401 / 403        → 返回登录页或无权限页
```

理由：藏卡片只是视觉手段，服务本身仍在内网可达；只有网关层校验才是真隔离（D-002）。

## 5. 主题与视觉

**完整规格见 `docs/主题.md`**（A–L 是你的原始设计，M 是由此推导的可执行 token）。本节只摘要在设计层面必须遵守的约定：

| 项 | 约定 |
|---|---|
| 世界观 | 艾米尔斯图书馆：一间温暖古典的私人书房，服务是书房里的器物 |
| 关键词 | 温暖、生活感、融合、克制奇幻、舒适易用 |
| 配色 | 胡桃木棕 + 羊皮纸白 + 哑光黄铜 + 琥珀暖光；**黄铜与琥珀禁止做文字** |
| 排版 | 标题衬线（子集化 woff2 ≤150 KB）、正文系统无衬线 |
| 动效 | 300–500ms，`cubic-bezier(.22,1,.36,1)`；视差可关；`prefers-reduced-motion` 全归零 |
| 机位 | 固定俯视 30°–60°，不允许自由飞行 |
| 分层 | 结构（HTML）→ token（变量）→ 皮肤（视觉）→ 背景（可插拔，静帧→WebGL） |
| 降级 | 手机/无 WebGL → 静帧 + 完整静态排版；搜索引擎 → 完整语义 HTML |
| 待定 | 暖木调 / 紫调二选一（等 V1 页面）；角色形态（建议 2D 立绘） |

**"静态元素融入场景"的实现方式**：不把 HTML 塞进 3D，而是把 3D 世界坐标投影成屏幕坐标，DOM 绝对定位过去。相机固定 → 投影只在断点变化时算一次。V1（静帧）与 V2（WebGL）共用同一份 `scene-anchors.json` 与同一套公式，换渲染器时 DOM 层不动。

## 6. 前端要求

| 项 | 要求 |
|---|---|
| 技术 | React 19 + TypeScript + Vite（已装） |
| 路由 | `/explore/:sceneId`（所有场景统一入口：书房、结构图、各功能区）｜`/blog/:slug`（长文正文，非场景）｜`/login`、`/register`｜`/admin/*` |

| 状态 | 只用 Query + `useState`，不引 Redux / Zustand |
| 目录 | 一区一文件夹（`X.tsx` + `X.module.css`）；文案在 `src/content/` |
| 语言 | 界面中文；代码注释中文、标识符英文 |
| 预算 | 首屏 JS gzip ≤ 80 kB（不含 3D chunk）；字体 ≤ 150 KB；静帧 WebP ≤ 300 KB |

## 9. 安全要求（十二条）

| # | 要求 | 不做会怎样 |
|---|---|---|
| 1 | 全站 HTTPS | 密码明文过公网 |
| 2 | 密码 argon2id 哈希 | 数据库泄露 = 密码泄露 |
| 3 | 管理员强制 TOTP；普通用户可选 | 管理员账号单密码即失守 |
| 4 | 登录限速 + 连续失败锁定 + 注册频率限制 + 图形验证码 | 脚本可无限猜密码、批量注册 |
| 5 | 邮箱验证与找回密码用**一次性、有时效**的 token | 链接可复用、可被枚举 |
| 6 | 会话：HttpOnly + Secure + SameSite，库里只存 token 哈希，可踢下线 | cookie 被脚本读取；泄露后无法止损 |
| 7 | 权限校验在服务端，每个接口显式声明 | 前端藏起来 ≠ 挡住 |
| 8 | 网关层 `auth_request` 校验后才反代内网服务 | 内网服务可被直接构造请求访问 |
| 9 | 上传：魔数校验 + 白名单 + 大小限制 + 随机名 + 剥 EXIF；media 目录禁执行 | 伪装图片被执行 |
| 10 | 所有用户输入（含**评论**）输出前消毒；评论限长 + 白名单标签 | 评论里插脚本偷 cookie |
| 11 | 管理动作只允许预设按钮、`shell=False`、审计先写后执行 | 一次误点或漏洞等于 root |
| 12 | 生产关闭 `/docs`；云上只代理必要路径；加 CSP 与安全响应头 | 扫描器拿到完整接口清单 |

**隐私（多用户新增）**：站点收集邮箱与阅读计数，必须有隐私说明页，写清收集什么、存多久、怎么删除账号。

## 12. 阶段路线（v0.3 重排）

| 阶段 | 产出 | 判据 | 要新学 | 估算 |
|---|---|---|---|---|
| **P0** 首页原型 | 静帧 + HTML 叠层 + 锚点投影的 L1 书房（无后端、无 3D） | 桌面与手机都能看；配色两版可对比；关动效仍可用 | CSS 布局、投影对齐、字体子集化 | 1–2 周 |
| **P1** 场景框架 + 第二个场景 | 场景注册表 + 锚点投影 + L2 结构图场景 + 部署到新子域 | 新增一个场景只加目录不改代码；公网可访问；每个热区可达 | 路由、数据驱动渲染、部署、DNS、证书 | 2–3 周 |
| **P2** 后端骨架 | FastAPI + `/api/healthz` + systemd + nginx 反代打通 | 公网 `/api/healthz` 通；杀掉进程 3 秒自恢复 | Python、venv、FastAPI、systemd、Tailscale ACL | 1–1.5 周 |
| **P3** 账号体系 | 注册（邮箱验证）+ 邀请开号 + 登录 + TOTP + 找回密码 + 会话管理 | 全流程跑通；未验证邮箱不能登录；token 一次性 | SQLAlchemy、Alembic、邮件发送、密码学常识 | 2–3 周 |
| **P4** 权限与网关 | 角色 + 逐服务 ACL + `/api/auth/verify` + nginx `auth_request` | 未授权访问内网服务被挡；越权接口返回 403 | nginx 子请求、会话与权限模型 | 1–2 周 |
| **P5** 写博客 | 编辑器 + 预览 + 传图 + 草稿 + 版本回滚（管理员） | 写一篇带图带代码的文章并保存，刷新不丢 | Markdown 渲染、上传安全、防抖 | 1.5–2 周 |
| **P6** 读博客 + 计数 | 列表/详情/标签/RSS + 阅读计数 | 手机可读长文；重复刷新不刷高计数 | 分页、HTML 消毒、去重策略 | 1–1.5 周 |
| **P7** 评论 | 自建评论：发表、审核、删除、防垃圾 | 评论注入脚本不执行；被删评论不再出现 | 表单校验、评论防滥用、通知 | 1.5–2 周 |
| **P8** 控制台 | 只读监控 + 预设动作 + 操作日志 + 自动备份 | 数据与 `htop` 误差 ≤5%；误点有确认；备份演练成功 | psutil、子进程安全、定时任务 | 1.5–2 周 |
| **P9** 逐个场景换 WebGL | 把 `manifest.renderer` 从 `still` 改成 `webgl`，场景数据与 DOM 层不动 | 背景 chunk 懒加载；关掉后全站可用；移动端不加载 | Three.js 生命周期、资源释放 | 3–5 周（首个场景），后续每个 3–7 天 |
| **P10**（可选）agent | 摘要、日志解释、只读自然语言查询 | LLM 只能调只读接口 | LLM 接口、工具调用 | 视情况 |

**累计估算**：以每周 8–10 小时计，P0–P8 约 **4–6 个月**，P9 再加 1–1.5 个月。这不是赶工项目。

**新增场景是一条独立的、可随时插队的工作流**：每加一个功能区 = 出静帧 → 标锚点 → 写 `manifest.json` → 配 DOM 卡片 → 接数据，约 3–7 天。所以"用户个人空间""新服务"这类需求可以在任何阶段插入，不打断主线。

**顺序理由**：P0/P1 是唯一"做完就能给别人看"的产出；P2 不通后面都是本地玩具；P3/P4 不做对，后面所有的内容与评论都建在露天平台上。

## 13. 可行性评估

| 能力域 | 风险 | 卡点 | 兜底 |
|---|---|---|---|
| P0 首页原型 | 低 | 无 | 已有静帧与机位参数，只差叠层 |
| 投影对齐 | 中 | 锚点坐标要手工标定 | 先用"数据里写死屏幕百分比"起步，再换成真投影 |
| 账号体系 | **高** | 零后端基础；邮箱发送要配 SMTP | 先只做邀请开号（无邮箱），跑通后再加自助注册 |
| 网关拦截 | 中高 | nginx `auth_request` 概念新 | 先在本地用 Nginx 试通，再上云 |
| 博客 | 中 | Markdown 管线与上传安全 | 服务端渲染 HTML 缓存，前端不背包 |
| 评论 | 中 | 防垃圾与审核 | 先"评论需审核后显示"，跑通再加自动过滤 |
| 控制台 | 中低 | 子进程安全 | 只做预设动作，永不开放命令 |
| WebGL 场景 | 高 | Three.js 学习曲线 | 静帧方案已可用，做不出来只是不升级 |
